# Codebase audit — 2026-07-29

Scope: full read-through of auth, permissions, all server actions, the rating engine,
queries, API routes, the uncommitted pagination work, and project config.

Revised the same day after re-verifying the top findings against the seed and the UI:
S1 turned out not to be reachable in the seeded configuration while S2 is, and B3 was
overstated and has been downgraded. Each is marked in place.

Health check at the time of the audit:

- `pnpm type-check` — clean
- `pnpm test` — 366 tests, 31 files, all passing
- `pnpm lint` — 0 errors, 2 warnings (`react-hooks/incompatible-library` in the
  admin rating item-number field)
- Uncommitted: pagination refactor across 8 files + new `components/ui/pagination.tsx`

Overall the codebase is in very good shape for its size: consistent conventions,
server-side permission checks everywhere, colocated tests, honest comments. Every
authenticated page carries its own `auth()` guard; every admin page re-checks the role;
every `/api` route authenticates itself. The findings below are ordered by how much they
matter, not by how easy they are to fix.

## 1. Security findings

### S1 — HIGH · `email` field grant allows account takeover

`email` is grantable to divisions (`app/(dashboard)/admin/permissions/field/actions.ts:13`),
and `updateStaff` (`app/(dashboard)/staff/[id]/actions.ts:117-120`) lets an editor with
that grant + `STAFF UPDATE` rewrite the email of **any** staff record — including an
ADMIN's. The chain:

1. Editor changes an admin's email to an address the editor controls.
2. Editor requests a reset on `/forgot-password` (public, only needs the email).
3. The activation link arrives at the editor's mailbox; setting a password signs them in
   **with the target's role preserved** (`app/(auth)/activate/[token]/actions.ts:46`).

Result: any editor whose division holds the `email` grant can become ADMIN. The same
chain takes over any USER account (submit achievements as someone else).

**Reachability — not open today.** `prisma/seed.ts` grants ННВ eleven fields and `email`
is not among them, so the chain has an open switch in the middle. It takes one admin
ticking «Email» in `/admin/permissions/field` to close it — where the field sits in the
same group as lastName, firstName and phone, and nothing warns that this particular
checkbox hands out account takeover. The severity is high, the current probability is
nil, and the real defect is that the UI makes it look clerical.

**Fix options** (pick one, simplest first):

- Move `email` out of `ALLOWED_FIELD_NAMES` — email changes become ADMIN-only. Cheapest,
  probably acceptable: emails rarely change.
- Or: in `updateStaff`, forbid non-ADMIN writes to any record whose `role !== 'USER'`.
  This also closes S3 below.
- Or (most work): keep the grant but require a confirmation link to the **old** address
  before an email change takes effect.

Whichever is chosen, add a regression test next to
`app/(dashboard)/staff/[id]/actions.test.ts` — the suite already covers the
`employmentRate` equivalent, so the pattern is there to copy.

### S2 — MEDIUM · `createStaff` bypasses the field-grant filter entirely

`createStaff` (`app/(dashboard)/staff/actions.ts:26-30`) spreads **all** parsed fields
into the insert for any caller who has `STAFF CREATE`. An editor can therefore set at
creation what they could never set through `updateStaff`:

- `employmentRate` — confidential, supposedly ADMIN-write-only;
- `divisionId` — a `PERMISSION_SCOPING_STAFF_FIELDS` member. Creating a person inside
  ННВ is not immediate escalation (the new account is role USER and roles are
  ADMIN-only), but it plants a record that becomes an ННВ editor the moment an admin
  ever promotes that person — and it contradicts the model's own comment that this set
  is "ADMIN only, for the same reason Division CRUD is."

**Reachability — open today, unlike S1.** ННВ is seeded with `STAFF CREATE`, and the
«Відділ» dropdown in `components/staff/staff-form-fields.tsx:253` is _not_ wrapped in the
`isAdmin &&` guard that protects ставка at line 322. Assigning a new person to any
division is therefore an ordinary UI action for an editor, not a forged request. Nothing
escalates immediately — the new row is role USER — but they would inherit that division's
grants the moment an admin ever promotes them, without any admin having consciously put
them there.

**Fix:** in `createStaff`, when the caller is an EDITOR, run the same filter as
`updateStaff` (division grants ∩ `isEditorWritableField`) and force
`divisionId`/`employmentRate` to null. The audit-log entry then also stops recording a
confidential value an editor typed in.

### S3 — MEDIUM · Editors can edit and delete accounts above their own level

`canManageEntity` is role-blind about the _target_: an editor with `STAFF UPDATE`/`
STAFF DELETE` may edit or hard-delete an ADMIN or another EDITOR (the only guard is
`isLastActiveAdmin`). Deleting an admin cascades their activities and kills their
account. This is a policy hole rather than a bug — decide it explicitly. Recommended
rule: non-ADMIN callers may only mutate records whose `role === 'USER'`; the same check
closes half of S1.

### S4 — LOW · No login throttling; user enumeration by timing

`authorize` in `lib/auth.ts` does a DB read + bcrypt compare per attempt with no rate
limit, and returns immediately when the email is unknown (no dummy compare), so response
timing reveals which emails exist. `/forgot-password` already has a 60s cooldown — login
has nothing. For an internal tool behind a university network this is acceptable at
launch, but add a simple per-IP/per-email counter (even in-memory) before real
deployment.

### S5 — LOW · Session lifetime of a deleted staff row

The `jwt` callback returns `null` when the staff row is gone — good. No action needed;
recorded here because it was checked.

## 2. Bugs and correctness risks

### B1 — Race: duplicate division rows / cap overshoot under concurrency

Two places do read-then-write without a uniqueness backstop:

- `upsertDivisionActivity` / `batchUpsertDivisionActivity`
  (`app/(dashboard)/division-data/actions.ts:91`, `:324`) — `findFirst` then `create`.
  Two editors saving the same cell simultaneously produce **two** APPROVED rows, and the
  rating then double-counts. There is deliberately no unique constraint on
  (staff, type, year) because NPP types are repeatable — but division rows are not.
- `createActivity` cap check (`app/(dashboard)/achievements/actions.ts:88-92`) —
  count-then-insert can exceed `maxPerYear` when the same person double-submits fast.

Likelihood at ~300 users is low, but the failure is silent and lands in official
numbers. **Fix:** a partial unique index enforces the division case at the DB level:

```sql
CREATE UNIQUE INDEX "Activity_division_one_live_row"
ON "Activity" ("staffId", "activityTypeId", "year")
WHERE "submittedByRole" = 'DIVISION' AND "status" <> 'REMOVED';
```

(then catch the P2002 in the action and retry as update). The NPP cap race can stay —
worst case is one extra row an ННВ moderator can discard — or use
`SELECT … FOR UPDATE`-style locking via `$queryRaw` if it must be airtight.

### B2 — `backfillProfileDerived()` failures crash an already-committed action

`activateTemplate` (`app/(dashboard)/admin/rating/actions.ts:175`), `reopenYear` (`:720`),
`updateActivityType` (`:328`) and `addActivityType` (`:554`) call the backfill **after**
their transaction commits, outside any try/catch. If the backfill throws (bad spec JSON
on one row is enough — `parseTypeSpecs` throws), the admin gets an unhandled server
error although the year _was_ activated/reopened. Wrap the call and return
`{ success: true, message: 'Активовано, але синхронізація профілів не виконана…' }`.

### B3 — Closed-year snapshot uses the code catalogue's section titles (latent)

`closeYear` (`app/(dashboard)/admin/rating/actions.ts:645`) writes
`SECTION_TITLES[number]` — the hardcoded 2026 titles — instead of the template's own
`RatingSection.title`.

**Downgraded on re-check.** An earlier draft justified this by "an admin renames a
section for 2027"; that is wrong. There is no `ratingSection.update` anywhere in the
codebase — section titles are written only by `cloneTemplate` (copying the source's
title) and `createTemplate` (from `SECTION_TITLES`), and the template editor edits
indicators, not sections. Titles cannot currently diverge from the constant without a
direct database edit, so the bug is unreachable.

It stays on the list because a snapshot meant to be authoritative should read its own
template's data rather than a code constant, and the section rows are already in reach
inside the transaction. Treat it as cleanup with the non-blocking items, not as a bug.

### B4 — «Перевірено» is keyed on `code`, against the project's own rule

`PUBLICATION_CODES` (`lib/rating/moderation.ts:6`) hardcodes
`publication_cat_a/b`. CLAUDE.md and the project memory both say "never key rating
behaviour on `code`" — an admin who builds a new publication indicator in the template
editor gets no verification toggle, silently. **Fix:** a `requiresVerification Boolean
@default(false)` column on `ActivityType`, exposed as a checkbox in the template editor,
seeded true for the two current codes. `setActivityVerified` then reads the row.

### B5 — Moderation rights hang on a division's display name

`canModerateRating` (`lib/rating/moderation.ts:26`) grants moderation to editors whose
division is **named** «ННВ» (`RATING_DIVISIONS.NNV`). Renaming the division in the UI —
which any admin can do — silently strips every ННВ editor of moderation and breaks the
export's «Дані внесені» mapping (`app/api/export/ratings/route.ts:74`) the same way.
**Fix:** a flag on Division (`canModerateRating Boolean`) or a settings row; name
matching should only ever be a seed-time convenience.

### B6 — Stale comment contradicts the no-queue design

`prisma/schema.prisma:46`: `NPP_SUBMISSION // NPP submits via profile, goes to PENDING
queue`. There is no pending queue — submissions are APPROVED at save. Comments like this
are exactly what misleads a future contributor (or model) into "fixing" moderation the
wrong way. Also `ActivityStatus.PENDING` itself is never written by any code path —
either delete the enum value in a migration or comment it as historical/reserved.

## 4. Recommendations for other models working on this codebase

Read `CLAUDE.md` fully before touching anything; it is accurate except where this audit
says otherwise. Beyond it:

1. **Trust the docs over your training data for Next.js.** This is Next 16 — proxy.ts
   instead of middleware, different caching. Check `node_modules/next/dist/docs/` first.
   Same for Prisma 7 (no `url` in schema, client at `@/lib/generated/prisma/client`,
   run `pnpm db:generate` after `pnpm install`).
2. **The permission model has two layers and three choke points.** Any change to Staff
   fields must be reflected in all three: `updateStaff`'s filters, `setFieldPermission`'s
   whitelist, and the queries' `includeConfidential`. Fixing S1/S2 means touching the
   choke points, not scattering new checks.
3. **Never key rating behaviour on `ActivityType.code`.** Indicators live in DB rows;
   read `parseTypeSpecs(row)` / `computeScore(type, evidence)`. If you need a new
   per-indicator behaviour (like B4's verification), add a **column**, not a code list.
4. **There is no approval queue.** Submissions are APPROVED at save; oversight is
   post-moderation with a reason. Do not "restore" PENDING — the schema comment claiming
   otherwise is stale (B6).
5. **Scores freeze at save; recompute moves rollups, not rows.** Editing a coefficient
   later must not rewrite existing `Activity.score`. Any mutation touching activities
   must call `recomputeRatingEntry` **inside the same transaction**.
6. **Follow the action-file idiom exactly:** `auth()` guard → permission check → Zod
   parse → `db.$transaction` with the mutation + `auditLog.create` (`diffChanges`) →
   `revalidatePath` → typed state return with a Ukrainian error string. Every existing
   `actions.ts` is a template; do not invent a new shape.
7. **UI text is Ukrainian, logic files are language-free.** Labels go to
   `lib/labels.ts`; new Staff fields also go to `ALLOWED_FIELD_NAMES` + `FIELD_GROUPS`.
8. **Commit via the `/commit` skill, never raw git.** Don't start dev servers or Docker —
   the user runs those himself.
9. **Write tests next to the file** (`*.test.ts`). The mocking pattern for actions is in
   `app/(dashboard)/staff/[id]/actions.test.ts`; for pure logic, `lib/rating/*.test.ts`.
10. **When fixing the security items, fix the model, not the symptom.** S1–S3 share one
    root cause: permission checks consider the _caller's_ rights but never the _target's_
    role. One helper (`canEditTarget(caller, targetRole)`) used by update/delete/create
    closes all three coherently.
