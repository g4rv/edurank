## 2. Settled — a saved ставка never rises on its own

**The rule (owner, 2026-08-27):** «in business logic it is impossible to just
have your rate being increased, it is a human decision to be done.»

«Тільки збільшити» was enforced against the формула **recomputed right now**.
The формула divides by sums over the whole кафедра, so it moved whenever
anything about the кафедра did — somebody archived, a cap edited, a сумісник
added — and the floor rose under people nobody had touched. Three places then
pushed them up to it, and one of them wrote to the database.

**Fixed.** The floor is now `StakeAllocation.formulaHundredths` — the формула
frozen at the last human save, which додаток 2 already prints for exactly this
comparison. Somebody with a saved ставка keeps it; somebody with **no** saved
row still opens on today's формула, which is correctly their first ставка.
`liftStoredAllocations` no longer raises anybody and no longer rewrites that
column.

**The line that was drawn:** your own Мін/Макс may move your ставка — that is a
decision about you — but the формула may not, because it moves for reasons that
are about other people.

### The rows on production — DONE (2026-08-27)

Decided by the owner: **keep the computer's values.** The four raises stand, and
Якуба's 1,00 → 0,75 was correct — his Макс was lowered, which is a decision

That reversed the earlier plan. While rolling the allocations back was still on

**Run: merged → backed up → deployed → repaired → checked on screen.** Five rows
updated; the drift query returns zero.

#### How it was actually run — SQL, not the pnpm script

`pnpm db:fix-employment-rate` **does not work on the production container.** The
`runner` stage of the Dockerfile copies only `.next/standalone`, `.next/static`
and `public` — there is no source, no `tsx`, no pnpm script, and the only Prisma
tooling is a bare CLI at `/opt/prisma` for migrations. Running it needs the
BUILDER image (`docs/deployment.md` §3), which needs SSH and a checkout.

The script is one statement, so it was run as SQL in Coolify's Postgres
terminal instead. Identical behaviour, including the safety property: the inner
join means somebody with no allocation at all is never touched, so a rate typed
by hand before розподіл existed is not wiped.

```sql
-- what would change
with y as (select year from "RatingTemplate" where "isActive" limit 1),
alloc as (
  select a."staffId", sum(a."proposedHundredths") h
  from "StakeAllocation" a
  join "StakeDistribution" d on d.id = a."distributionId"
  join y on y.year = d.year
  group by a."staffId")
select s."lastName", s."employmentRate" as now, al.h / 100.0 as will_be
from alloc al join "Staff" s on s.id = al."staffId"
where coalesce(s."employmentRate", 0) <> coalesce(al.h / 100.0, 0);

-- write it (same CTEs)
update "Staff" s
set "employmentRate" = al.h / 100.0
from alloc al
where s.id = al."staffId"
  and coalesce(s."employmentRate", 0) <> coalesce(al.h / 100.0, 0);
```

**Deploy before repairing.** On the old code another cap edit re-creates the
drift immediately.

#### What can still make the cache stale

All three app writers now recompute it in the same transaction —
`saveDistribution`, `liftStoredAllocations` and `updateStaff`'s cleanup — so the
bug above cannot recur. Two paths remain, neither of which caused it:

- **Deleting a кафедра** cascades allocations away without recomputing. Not
  reachable in practice: `deleteDepartment` refuses a кафедра with any staff
  attached, archived included.
- **Activating a new rating year.** The cache means «sum for the ACTIVE year»,
  so everybody keeps last year's figure until the new year is spread. Arguably
  what you want — better than every ставка reading 0,00 in January — but stale
  by definition.

Both exist only because there are two copies of one number. §4 is the permanent
answer.

## 4. Deferred — database restructure

`Staff.employmentRate` is a **cache** of `Σ StakeAllocation.proposedHundredths`
for the active year, across every кафедра that pays somebody. Two places hold one
number, and this is the second one-off repair script written for that field
(`fix-employment-rate.ts`, `fix-rating-rounding.ts` being the pattern).

History — it was never designed as a cache:

| When                   |                                                                            |
| ---------------------- | -------------------------------------------------------------------------- |
| May 2026               | `employmentRate` in the very first migration: a hand-typed contract rate   |
| 2026-08-21 (`d0f92e8`) | `saveDistribution` starts writing it — it becomes derived                  |
| 2026-08-24             | сумісництво makes it a **sum across кафедри**, so it matches no single row |
| now                    | `updateStaff` drops it from input; nobody can type it                      |

**Dropping it is safe on the data.** Both dev and prod return **0** people
holding a rate with no allocation behind it, so the column can be rebuilt
entirely. Three readers: the `/staff` «Ставка» column, sorting by it, and the
edit form's display. Only sorting wants a column — and `/rating` already sorts
~330 rows in JS.

**Deferred by the owner (2026-08-27):** restructure when things settle; for now
fix bugs and improve the day-to-day experience. Recorded here so the reasoning is
not re-derived.

The check, for whenever this is picked up:

```sql
select s."lastName", s."firstName", s."employmentRate" as orphan_rate,
       (select count(*) from "StakeAllocation" a where a."staffId" = s.id) as allocations_any_year
from "Staff" s
where s."isSystem" = false
  and s."employmentRate" is not null and s."employmentRate" <> 0
  and not exists (
    select 1 from "StakeAllocation" a
    join "StakeDistribution" d on d.id = a."distributionId"
    join "RatingTemplate" t on t.year = d.year and t."isActive"
    where a."staffId" = s.id);
```

## 5. Shipping these

**Only a schema change needs a maintenance window.** Everything in §1 and §2 is
code-only — Coolify restarts the container and that is the whole outage.

| Work                           | Window?                                             |
| ------------------------------ | --------------------------------------------------- |
| The bug fixes                  | No                                                  |
| The ставка rule (§2)           | No — but announce it: numbers on the grid will move |
| The five-row repair (§2)       | No — done 2026-08-27                                |
| Dropping `employmentRate` (§4) | Yes                                                 |

**Prefer a quiet weekday morning to 2am for code.** At 2am nobody is around to
notice it went wrong, and the bad state is live until 9am. Night is for the
schema migration, where you want no writes mid-flight.

The §2 rule shipped on 2026-08-27 with only 3 of 31 кафедри holding a saved
розподіл, which was the cheap moment to do it: every кафедра saved before the
change had its floor computed the old way. Worth remembering if a comparable
rule ever moves again — this query says how much mixed state you would be
creating:

```sql
select count(*) as saved_splits,
       (select count(*) from "Department") as total_departments
from "StakeDistribution"
where year = (select year from "RatingTemplate" where "isActive" limit 1);
```

**Restore a backup once, before the §4 restructure.** (A backup was taken
before the §2 repair on 2026-08-27, and that repair went through cleanly.) `deployment.md` §7 has the
procedure and it touches nothing live. Until it has been done, the backup is a
hope — and a restructure later leans on it entirely. A backup buys a retry
window of minutes, not an indefinite undo: once prod runs a day on a new shape,
restoring costs that day. Prisma has no automatic down-migration; plan forward,
use expand → backfill → contract.

Strict TypeScript plus Prisma's generated types is what makes restructuring
realistic here — dropping a column is a compile error, not a runtime surprise,
and 1145 tests sit behind that.
