## 2. Open — needs a decision

### 2.1 A saved ставка must never rise on its own

**The rule (owner, 2026-08-27):** «in business logic it is impossible to just
have your rate being increased, it is a human decision to be done.»

«Тільки збільшити» is currently enforced against the formula **recomputed right
now**. The formula moves whenever the кафедра changes — somebody archived, a cap
edited, a сумісник added — so the floor rises under people nobody touched, and
three places push them up to it:

- `distribution-grid.tsx` seeds each row at `max(stored, formula-today)`
- `saveDistribution` refuses anything below `formula-today`
- **`liftStoredAllocations` rewrites stored rows up to `formula-today` — this one
  writes to the database.** Audit label: «перерахунок після зміни лімітів».

Seen on prod: five people carry a raise nobody typed, four of them from a single
cap edit at `2026-08-25 06:25:37.777`, and one (Якуба) from `2026-08-27 08:01`.

**Proposed fix:** measure «тільки збільшити» against the formula frozen at the
last human save — `StakeAllocation.formulaHundredths`, which додаток 2 already
prints for exactly this comparison. Somebody with a saved ставка keeps it;
somebody with **no** saved row still opens on today's formula, which is correctly
their initial automatic ставка. Note `liftStoredAllocations` currently overwrites
`formulaHundredths` too, so that column must stop being rewritten before it can
be trusted as the reference.

It also removes the deadlock the current design keeps fighting (Кафедра
географії, Кафедра соціальних комунікацій — see the comments in `settle.ts`,
`formula.ts` and `saveDistribution`).

**Splits in two halves.** The _code_ half needs no decision and stops prod
writing wrong numbers. The _data_ half — below — does.

### 2.2 The five raised rows on prod

| Person           | cache | allocation |
| ---------------- | ----- | ---------- |
| Вовченко Роман   | 0,25  | 0,35       |
| Девко Світлана   | 0,35  | 0,50       |

| Яременко Людмила | 0,35  | 0,50       |
| Якуба Василь     | 1,00  | 0,75       |

The cache holds the last human decision; the allocation holds the machine's
raise. So **do not run `pnpm db:fix-employment-rate`** — it copies allocation →
cache, which was written for a different cause (rows spread before `d0f92e8`
existed) and would now overwrite the human's number with the machine's.

Open: roll the allocations back to the human's number, or accept the raises?
The audit log has the answer per person — a «розподіл ставок» entry carries the
before/after a human saved.

**Якуба is the opposite case**: 1,00 → 0,75, because someone lowered his Макс
below his saved ставка. Open: is a cap edit an explicit enough decision for pay
to follow it _down_?

## 4. Deferred — database restructure

`Staff.employmentRate` is a **cache** of `Σ StakeAllocation.proposedHundredths`
for the active year, across every кафедра that pays somebody. Two places hold one
number, and this is the second one-off repair script written for that field
(`fix-employment-rate.ts`, `fix-rating-rounding.ts` being the pattern).

History — it was never designed as a cache:

| When                   |                                                                            |
| ---------------------- | -------------------------------------------------------------------------- |
| May 2026               | `employmentRate` in the very first migration: a hand-typed contract rate   |
| 2026-08-21 (`d0f92e8`) | `saveDistribution` starts writing it — it becomes derived                  |
| 2026-08-24             | сумісництво makes it a **sum across кафедри**, so it matches no single row |
| now                    | `updateStaff` drops it from input; nobody can type it                      |

**Dropping it is safe on the data.** Both dev and prod return **0** people
holding a rate with no allocation behind it, so the column can be rebuilt
entirely. Three readers: the `/staff` «Ставка» column, sorting by it, and the
edit form's display. Only sorting wants a column — and `/rating` already sorts
~330 rows in JS.

**Deferred by the owner (2026-08-27):** restructure when things settle; for now
fix bugs and improve the day-to-day experience. Recorded here so the reasoning is
not re-derived.

The check, for whenever this is picked up:

```sql
select s."lastName", s."firstName", s."employmentRate" as orphan_rate,
       (select count(*) from "StakeAllocation" a where a."staffId" = s.id) as allocations_any_year
from "Staff" s
where s."isSystem" = false
  and s."employmentRate" is not null and s."employmentRate" <> 0
  and not exists (
    select 1 from "StakeAllocation" a
    join "StakeDistribution" d on d.id = a."distributionId"
    join "RatingTemplate" t on t.year = d.year and t."isActive"
    where a."staffId" = s.id);
```

## 5. Shipping these

**Only a schema change needs a maintenance window.** Everything in §1 and §3 is
code-only — Coolify restarts the container and that is the whole outage.

| Work                           | Window?                                             |
| ------------------------------ | --------------------------------------------------- |
| The bug fixes                  | No                                                  |
| The ставка rule (§2.1)         | No — but announce it: numbers on the grid will move |
| The five-row repair (§2.2)     | No — seconds. Announce, do not shut down            |
| Dropping `employmentRate` (§4) | Yes                                                 |

**Prefer a quiet weekday morning to 2am for code.** At 2am nobody is around to
notice it went wrong, and the bad state is live until 9am. Night is for the
schema migration, where you want no writes mid-flight.

**What actually decides the timing of §2.1** is how many кафедри have already
saved a розподіл — every one saved before the change has its floor computed the
old way:

```sql
select count(*) as saved_splits,
       (select count(*) from "Department") as total_departments
from "StakeDistribution"
where year = (select year from "RatingTemplate" where "isActive" limit 1);
```

Dev has 3 of 31. Cheap now, careful later.

**Before the §2.2 repair: restore a backup once.** `deployment.md` §7 has the
procedure and it touches nothing live. Until it has been done, the backup is a
hope — and a restructure later leans on it entirely. A backup buys a retry
window of minutes, not an indefinite undo: once prod runs a day on a new shape,
restoring costs that day. Prisma has no automatic down-migration; plan forward,
use expand → backfill → contract.

Strict TypeScript plus Prisma's generated types is what makes restructuring
realistic here — dropping a column is a compile error, not a runtime surprise,
and 1145 tests sit behind that.
